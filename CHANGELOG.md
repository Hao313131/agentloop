# Changelog

Newest first; each entry maps to a commit and tests in the history. Numbers come from the offline deterministic model and fictional data — they show the flow is correct, not the quality of a real model.

## 2026-10-21

**Renamed the project to AgentLoop**: the product used to be called LoopDesk. The display name is now AgentLoop (README, the console page title, the `agentloop.access` log prefix); the environment variable prefix is `AGENTLOOP_`; the Python package is `agentloop` and the frontend package is `agentloop-console`; the SQLite file defaults to `agentloop.db`; the Prometheus counters are `agentloop_runs_total`, `agentloop_tokens_total` and `agentloop_run_errors_total`; the MCP tools are `agentloop_search_knowledge`, `agentloop_get_order` and `agentloop_track_shipment`; the shared demo password is `agentloop-demo`; the image user and the docker-compose PostgreSQL user, password and database are all `agentloop`; and the GitHub Pages base path is `/agentloop/`, so the static demo moved to https://hao313131.github.io/agentloop/. Nothing about behaviour changed — the rename is 69 files and 337 substitutions, and the 295 backend tests still pass.

## 2026-10-20

**WhatsApp channel isolated per tenant (N-033)**: WhatsApp had a single global verification token and one app, so a token from the Harbour & Home store hitting `/whatsapp/rostr/events` still returned 200 and created a user and conversation under the Rostr Cloud docs; every tenant's replies also went out from that one app. Now each tenant has its own app (`AGENTLOOP_WHATSAPP_APPS`): the callback only accepts that tenant's token, and the `app_id` in a schema-2.0 event must also match; replies, approval results, and human replies all go out from that tenant's app, with the access token cached per app (previously a single cache slot meant the second tenant got the first tenant's token). The old single-app variables only worked with `AGENTLOOP_WHATSAPP_TENANT`, and two tenants sharing an app_id failed to start. Also fixed a 500 when the callback body wasn't an object or was invalid JSON: a non-object body now returns 400, and events with malformed fields are ignored. Five new tests failed on the old code; dropping the app_id check made the cross-tenant test fail.

**Live demo (GitHub Pages)**: a static build of the console, no backend needed. At deploy time CI starts a real backend (offline model, fictional data) and, by script, walks a customer's questions, an agent's approval and human reply, a ticket pickup, an admin changing a limit, and the regression eval, recording every endpoint response the console would request plus the event stream of each sample question on the chat page (`app/ops/record_demo.py`); the browser replays them via `demo/replay.ts`, and submit-type actions don't take effect. A test checks the chat page's sample questions match the recording script, that each one replays, that staff pages have data, and that no login credentials or password hashes are in the recording. Added `docs/CASE_STUDY.md`. During recording the offline model also filed a ticket for policy questions like "how quickly does a P1 incident get responded to?" — noted as to-fix.

**Runs left behind by a killed process are cleaned up by a scheduled task**: streaming runs execute in a background thread, so when a process is killed by kill -9, OOM, container reclaim, or a publish that doesn't wait for the request to finish, no exception handler runs and the run record hangs forever at "running": metrics keep counting it, the trace never ends, and the customer who just got a refund gets no answer. Added `python -m app.ops.stale_runs` (every minute, plus once at startup): runs past the cutoff are marked failed and their OTel trace exported. The cutoff = run deadline + the 5s follow-up-rewrite cap + 3× model timeout + 60s (default 290s), covering the rewrite and LLM verification the run deadline can't see; a run recovering from approval counts from the approval decision time. If the customer is still waiting, a system note is left in the conversation (WhatsApp chats are re-answered by the channel compensator; chats already in handoff or where the customer already re-asked get none). The dashboard gained an "interrupted process" error category instead of "other". Time-based rather than "end everything at startup", so multi-instance deploys don't wrongly kill another instance's in-flight run; each run ends with a single conditional update, so several instances scanning at once process it only once. A new test does a real kill -9 (start the service, kill it mid-streaming-reply, then the cleanup task ends the run); dropping the cutoff, the status condition, the recovery-time check, the startup run, or any notification condition fails a test.

**Completed ops exports (N-023)**: only run logs, feedback, and approvals were exported, all in UTC. Added three exports — full conversation (every message, role, and author, excluding eval sessions), tickets (promised deadline, whether on time `sla`, outcome), and human-takeover records (queueing, first reply, wait seconds, handler, end time); all export times now use the tenant timezone, with column names noting the timezone (e.g. `created_at (Australia/Sydney)`); exports are still audited. Writing the human-takeover export exposed a wrong average-first-response on the dashboard: a conversation handed off twice where the first ended with no reply borrowed the second's reply (the test over-counted by an hour); fixed to count only replies during that handoff, with the dashboard and export sharing the definition. Four tests failed on the old code.

**Connecting a real model no longer stalls startup, and you can self-test first (N-032)**: the demo's prefilled conversations were on by default and called the model synchronously during startup: a wrong key took ~100s to start, and a hung upstream meant no startup after 6 minutes, with `/api/health` unreachable meanwhile. Now prefilled conversations default on only with the offline model; with a real model they default off, and turning them on explicitly runs in a background thread. Added `python -m app.ops.llm_check`: one minimal request per tier, reporting a categorised reason and fix advice on failure (shared with the dashboard's error categories), exit 1 on failure. `/api/ready` deliberately doesn't check the model: an unavailable model still hands off or quotes policy. Three tests failed on the old code.

**Error rate on the dashboard (N-037)**: when all models were down, the overview's resolution, handoff, and refusal rates were all 0, hiding any incident. With the model-failure fallback (N-031) customers still got replies, which would completely mask an outage, so the overview gained `failures`: errored run count, error rate, last-15-minute count, breakdown by cause (model unavailable, request rejected, timeout, breaker open, customer disconnected), and the last error; a top banner appears when there were errors in the last 15 minutes. Errored runs aren't counted as self-service-resolved, or one outage would lift the resolution rate. Prometheus gained `agentloop_run_errors_total`, and DEPLOYMENT gives the alert rule. In the same commit, fixed N-031's breaker count: pointing the service at an unreachable address showed "5 failures in 30s" never filled when traffic was low or the model hung (each failure taking 45s), so the breaker never opened; changed to open after 3 consecutive failures and clear on any success. The degraded reply quotes the first two related passages (the first isn't always the answer, e.g. "how do I issue an invoice") and drops list markers.

**Pause approval: save first, then notify**: when the agent paused to wait for approval, it used to submit the approval, send the Slack notification, and emit the `approval_required` event before saving the state needed to resume (the pending call, message history) and "waiting for approval". The approval was in the queue the moment it was submitted, so two failure modes appeared: a reader stopping at `approval_required` left the run failed with the resume state unsaved, and every later approval raised `KeyError: 'pending'` and bounced back to pending, never approvable; or an approver acting before the Slack notification finished hit the same error first time. Now the approval, the resume state, "waiting for approval", and the pause reply commit in one transaction, and only then are the notification and event sent, with event order unchanged. Three tests failed on the old code: stop at `approval_required` then approve successfully with the refund executing once and the customer getting the resumed reply; approve during the notification with success first time; reader stops during resume with the run completing cleanly, no error.

**Model-failure fallback (N-031)**: when the model service errored fast, every message got "temporarily busy, please retry later or hand off to a human", and doing what it said and sending "hand off" failed too, because handoff itself needed the model to decide; a hung model meant waiting the full 90s. Now: ① explicit human requests ("hand off", "I want a human agent", "I want to complain", excluding negations and questions like "what hours is the human agent on") are caught by rules and go straight to a human without the model, cutting the eval gate's tokens from 61737 to 60888; ② when both tiers fail, degrade: knowledge questions quote the policy verbatim with a citation (not cached), order-related or uncitable ones go to a human, the run still records the error; ③ each model has a circuit breaker that, after 3 consecutive failures, pauses that model for 60s then lets one probe call through; ④ the whole-run time budget dropped from 90s to 45s; the follow-up rewrite used to be outside the budget (a hung model could make it wait 3×60s) but now caps at 5s, and an open breaker uses the rule rewrite directly; ⑤ if the model errors after approval passed and the refund already executed, the customer now sees the refund number and amount instead of "temporarily busy". Six tests failed on the old code (hand off on model failure, skip the model only on explicit request, degraded reply vs handoff, breaker and probe, model error after refund executed, follow-up rewrite not waiting on the failed model).

**Dashboard and order dates by tenant timezone (N-024, migration 0018)**: the dashboard split days by UTC, so traffic at 6am Beijing time on 10-20 counted under 10-19 while every other time on the page was local; "last 7 days" was a rolling 168 hours with the 8th day's tail appended at the right edge. The tool's payment and receipt dates told to customers were also UTC, so an order received before 8am was reported as received the day before. Tenants gained `timezone` (an IANA name, default `Australia/Sydney`, changeable via `PATCH /api/tenant`, invalid names return 400 and are audited); the dashboard's "last N days" are N calendar days in the tenant timezone (including today), split by local date with the timezone noted; order dates use the local date. The image installs `tzdata`, and CI resolves a timezone once inside the built image.

**Ticket text included in erase right and retention**: building the ticket workbench (N-019) revealed ticket titles and descriptions are the customer's words and outcomes are written to the customer, yet neither the erase right nor retention touched the ticket table. Now the erase right scrubs all of a customer's ticket text; retention scrubs closed-ticket text past the window, keeping status, priority, and time for stats and leaving open tickets alone. Each has one test that failed on the old code.

**Staff actions into the audit log (N-022)**: the audit log previously only recorded admin config changes; agents approving or rejecting refunds, exporting CSV, and sending or ending human replies left no record. Now those actions plus ticket pickup and processing write a signed audit record: approvals record amount, order, and opinion, committed in the same transaction as the approval decision (and a second record on execution failure rolling back to pending, recording only the error type since the message might leak data); exports record days and row counts, returned only after the record commits; human replies record only the conversation and message ID, leaving the words in the conversation under retention. The audit page filters by category (`GET /api/audit?category=approval`) so a day's human replies don't bury a limit change.

**Staff ticket workbench (N-019, migration 0017)**: when the agent filed a ticket promising "technical support will contact you within 4 hours", no staff page, endpoint, or export could see those tickets, so the promise was never kept. Added a "Tickets" page: open tickets sorted by the promise made to the customer, showing time left or overdue; an agent picks one up (conditional update, only one of two simultaneous pickups wins), writes the outcome and closes it, and the outcome is written into the source conversation as a human-agent message (a WhatsApp customer is also pushed, and a send failure doesn't block closing); closing with no pickup records who closed it. The promised deadline is written to `due_at` at creation, so later changing the tenant SLA doesn't rewrite what was told to the customer; the dashboard pins a reminder when there are overdue tickets. The list queries in two passes (all open, plus the 100 most recently closed) so a long close history never pushes pending tickets off the list. The end-to-end walkthrough gained a fourth path (customer reports fault → agent picks up and processes → customer sees it in chat); deliberately writing the close endpoint's path wrong failed that case.

**After a refund rejection, stop telling the customer "expected in 1–3 business days" (N-020)**: the offline model treated a rejection as a successful refund and searched for receipt timing; the sentence-by-sentence check only verified a source, and that sentence had one in policy, so it passed. Now a rejection replies with the rejection reason and next step (re-submit with more evidence or hand off); the verifier gained a rule: when the last refund was rejected or failed to submit, a sentence saying money will arrive conflicts with the tool result and the whole reply is `blocked`.

**Frontend end-to-end tests into CI**: Playwright walks three cross-role critical paths as customer, agent, and admin (an evidenced reply and its trace, an over-limit refund approved then the customer auto-receiving the result, a handoff then an agent reply; later a ticket path was added), failing on any console error, uncaught exception, or 5xx. Deliberately breaking three frontend spots (the customer page stopped polling, a wrong approval endpoint path, the customer seeing a staff-only "trace" button) each got caught by its case.

**Flaw-finding loop**: a scheduled task reviewed the system as a customer, an interviewer, and a red-teamer; the first round found 12 issues (1 P0, 5 P1, 6 P2), all fixed. Each started with a test or eval case that would fail before the fix.

- Order numbers adjacent to Chinese characters weren't recognised: Python's `\b` treats Chinese as word characters, so switched to explicit assertions.
- After-sales timing moved into the tool layer: beyond 15 days is flatly refused, 7–15 days goes to a human to verify, measured from request time; limits are tenant config (migration 0003).
- Approval reasons split into an approver version and a customer version; risk thresholds, cost, model, and injection-hit rules are no longer sent to the customer.
- Phone and card masking by real writing habits (+86, spaces, hyphens, grouping).
- Spoken-language questions: fixed tokenisation, added stopwords; the relevance threshold now scores against the replaced canonical wording.
- The offline model understands negations like "no need to hand off".
- Login rate-limiting only consumes failed attempts, still strictly limiting concurrent guessing; parameter-validation failures return an English message without echoing input.
- Consecutive follow-ups rewritten by a "topic / question" frame; full-width order numbers, English logistics questions, and multiple requests in one sentence all handled.

**Second flaw-finding round**: an interviewer's view found 6 issues (1 P0, 2 P1, 3 P2), all fixed, again each starting with a pre-fix failing test.

- On PostgreSQL, after switching to batched trace writes, querying the tool list from the DB at run end returned an empty list: handoff was marked complete and the answer cache stopped writing. Tools now track in memory; CI's SQLite job also runs the full suite in batched mode, with a new test that "both write modes give identical business results".
- The data flywheel could publish a correction conflicting with current policy ("within 3 days" vs "1–3 business days", different units, missed by conflict detection): conflict detection converts units by dimension; before publishing it's checked against the passages the reply cited, returning 409 on conflict and only activating the case after reviewer confirmation, with its regression case not auto-enabled. Confirmed conflicts go into the knowledge base's to-verify list (migration 0008 records the conflict source); until resolved, customer questions whose retrieval contains both sides go to a human instead of stating either; the dashboard pins the pending-conflict count, longest wait, and resulting handoffs.
- Self-service rate was counted per run and counted refusals as resolved: now resolution, handoff, and refusal rates are per conversation, with refusals separate.
- Hitting the step cap or a model refusal only marked "hand off" without filing a ticket: now it truly hands off and the customer enters the queue.
- A single run had no overall deadline (worst case ~36 minutes): added a run deadline (default 90s), with model-call timeout and retries tightened to the remaining budget, handing off on timeout.
- Login rate-limiting was per-process, so with 4 workers 21 of 40 bad logins for one account reached password check: on PostgreSQL moved to DB counting (migration 0006), shared across workers.

**Human-in-the-loop**

- Handoff is a conversation state: the agent goes silent, the customer's message is left for a human, and no run is created; added a human-takeover page (queue, reply, return to bot), with WhatsApp human replies pushed straight back to WhatsApp.
- Three-layer idempotency: in-runtime interception, tool reuse of the open ticket, and partial unique DB indexes (migrations 0004, 0005).
- The dashboard gained "pending approval / waiting for human": people being served, longest wait, first-response time.

**Retrieval**

- Relevance-threshold probe (`python -m app.evals.gate_probe`) measured both directions at once: spoken questions passing 26/33 → 33/33, out-of-scope questions blocked 14/20 → 16/20.
- Compound words absent from the knowledge base don't match on a sub-word alone ("can I pay on delivery?" no longer answers with "ships within 48 hours of payment").
- The hard set grew to 9 cases, recording what lexical methods can't do: 4/9.

**Performance**

- cProfile showed the same knowledge sentences re-tokenised repeatedly; a cache lifted throughput 11%–15%.
- Added a manually triggered PostgreSQL / multi-worker load workflow: at concurrency 16, PostgreSQL with 4 workers hit 103.6 RPS / p99 222ms, single worker 45.1 RPS / p99 470ms.
- Retrieval scaled linearly with knowledge-base size (both recall paths computed in Python per passage, 391ms for 20k passages): BM25 moved to an inverted index and vector scores to one matrix multiply, dropping 20k passages to 10ms and 50k to 27ms; added `python -m app.evals.retrieval_bench`; tests guarantee ranking identical to scanning one by one. After a document change the rebuild reuses tokenisation of unchanged passages and builds the vector matrix straight from bytes: editing one doc in a 50k set dropped from ~10.5s to 1.4s (the tokenisation-cache key adds a text hash, since SQLite reuses deleted-row IDs). Index-staleness checks switched to comparing the tenant's knowledge version number (migration 0013, bumped in the same transaction as passage changes), no longer recounting all passages: at 50k passages each check went 2.63 → 0.06ms. Indexes for all tenants are pre-warmed in the background at startup, and `/api/ready` returns 503 until warm so the first customer after a restart doesn't wait for indexing.
- The `Server-Timing` response header records in-app time, so load tests separate in-app from out-of-app latency.
- On PostgreSQL, trace writes at the run's commit point cut per-request commits from 9.3 to 3.0 and lifted same-run throughput 39%–47%; dropping only the fsync-wait async commit showed no gain and was reverted.

**Reliability and security**

- The run's exception handling only caught exceptions inside the agent loop: errors before entering the loop (cache query, follow-up rewrite, routing), or a reader stopping early (generator closed, `GeneratorExit` isn't an `Exception`), left the run stuck at "running". Streaming already ran the run in its own thread, but scripts and future channels whose reader stops early lacked that protection, and pre-loop errors hit every reader. Now the whole span after the run record is created sits in one guard: exceptions are recorded as `failed` with the error; on early stop, unfinished runs are marked `failed` (client disconnected), while runs already saved as complete or paused-for-approval are untouched; `GeneratorExit` is recorded then re-raised, not swallowed.
- On login, an unknown email returns 401 immediately, but a known email did one PBKDF2 (200k iterations, ~45ms locally) before returning, so response-time comparison could enumerate which emails had accounts. Now an unknown email runs the same computation against a fixed placeholder hash. Tests count the PBKDF2 calls (count, salt length, iterations) per failed login rather than timing, giving stable results.
- Two refund requests for the same order arriving together double-paid (a read-then-write race, reproduced with a forced interleave: one $39.90 refunded twice); fixed with a conditional update that claims the order, so only one request wins.
- Two admins publishing a knowledge patch at the same time: the first publish created two patch documents, and every later publish failed; later publishes could also overwrite each other, losing the other patch. Fixed to claim the patch with a conditional update and publish serially per tenant.
- During streaming, if the customer closes the page the run still finishes, the answer is written to the conversation, and no "running" record is left behind.
- Tamper-proof audit records (migration 0015): each record has a tenant-scoped sequential number and an HMAC signature, with the key outside the database; `GET /api/audit/verify` and the audit page show the check result, so editing or deleting records directly in the DB is detected.
- After exercising the erase right, the account can't log in, but credentials issued before (valid up to 12 hours) still worked. Credentials now carry the user's version number (migration 0014), bumped on erase so old credentials die immediately; credentials issued before the upgrade are treated as version 0, and the upgrade itself drops no one.
- The second tenant (rostr, SaaS) evals grew from 3 to 10 cases and entered the CI gate (CI previously only ran the e-commerce tenant). Adding cases exposed that spoken normalisation only covered e-commerce phrasing, so "the export button does nothing, how long until someone looks at it" was refused; after adding general support-centre phrasing, both tenants' gates, threshold probes, and hard sets were unchanged.
- The eval gate gained 6 red-team cases (46 → 52): impersonating approval, faking a system notice, refunding someone else's order, repeating a bank card number, extracting the system prompt, and impersonating an admin to change limits. The docs note which pass trivially under the offline model and only gain discrimination with a real model.
- Approvals tiered by amount (N-021, migration 0016): previously any agent could approve any refund, and four-eyes only blocked "approving your own", while the requester is usually the customer. Now refunds above the tenant tier line (default $500, tunable via `PATCH /api/tenant`) need an admin; agents can still reject; a rejection must give a reason, and the customer no longer sees "review opinion: none". The approval page flags cases needing an admin.
- External anchors for audit records: after each record commits, its number and signature are written to the structured log, and `python -m app.ops.audit_anchor_check` reconciles log against database, covering the blind spot signature checks miss — "delete the newest few and lower the counter".
- A second independent review found 6 more issues, each reproduced with a test then fixed: after swapping the vector model without rebuilding the index, the matrix multiply errored on every search and the failed-search refusal got cached for a day (now fall back to BM25 on dimension mismatch, don't cache tool-failed answers, and include the vector model and dimension in the cache key); a verified conflict matched only by sentence, so the same sentence appearing as a new conflict in another doc was missed (now matched by "document + sentence"); audit verification let unsigned records pass and errored on non-ASCII signatures (now unsigned fails, with a one-off backfill command `python -m app.ops.audit_backfill`); the audit key was derived from the JWT key, so rotating JWT would fail all old records (production config requires a separate key); deleting a document and resolving a conflict took locks in opposite order, risking a deadlock on PostgreSQL (now always lock the tenant row first, and resolve conflicts with a conditional update); a rolling upgrade where the old version wrote the knowledge base without bumping the version number (noted in the upgrade notes).
- An independent review of the day's changes fixed 4 issues (2630137): a failed correction draft retried and lost the case and patch; the compensator's claim timestamp was too early, double-answering on overlapping runs; a verified knowledge conflict reopened after index rebuild; on PostgreSQL, editing a doc and publishing a patch locked the tenant row, blocking same-tenant conversation writes.
- After approval passed, sending the result to a WhatsApp customer through an unreachable WhatsApp API made the approval endpoint return 500: the refund had actually executed and committed, yet the approver saw failure and clicking again got "already processed". Changed to best-effort send: failure is only logged, the endpoint returns normally, and tells the approver the notification wasn't sent but the result is in the conversation.
- Feedback de-duplication (migration 0012): one person clicking "useful / not useful" twice on the same reply recorded two entries, and the dashboard's feedback count counted clicks not people; submitting the same correction twice created two eval cases and two patches. Now each person keeps one rating per reply (later click overwrites), and a duplicate correction returns the first result. Also fixed: when a customer reopened a conversation, the endpoint returned the agent's correction content on that reply (internal data); now only the person's own feedback is returned.
- Every line of the access log was `tenant_id: null, user_id: null`: auth ran in a thread pool, mutating a copy of the context, so the middleware writing the access log couldn't see it. Fixed by having the middleware create a request-scoped mutable object that auth fills in, shared by both.
- OpenTelemetry export (`AGENTLOOP_OTLP_ENDPOINT`): each run exports as one trace on completion, model and tool calls named per GenAI semantic conventions with token usage; a run paused for approval exports once at final completion including the pre-pause steps; only metadata is exported. Also fixed: with batched trace writes, all spans' start times were recorded as the write time.
- Management-operation audit (migration 0009): previously only the agent's runs and approvals were traceable — who changed the auto-refund limit from 50 to 500, who changed the refund policy, was unqueryable. Now every change to risk limits, after-sales deadlines, knowledge docs, patches, conflicts, eval cases, and the erase right records operator, time, request ID, and what changed, viewable by admins on the "Operation audit" page.
- Knowledge-base docs can be edited online (previously the flywheel said "edit the original document" but you could only delete and re-upload): saving carries the version seen at edit time, so someone editing from the same version gets a 409 on save rather than overwriting; after save it re-indexes and checks conflicts.
- When a WhatsApp customer's first two messages were processed simultaneously (two workers, or a worker and the compensator), both "create if missing" raced: either a unique-constraint collision on user creation returning the fallback line, or the same group chat got two conversations and every later message failed on finding two. Fixed to "query first, insert on failure reads the other's creation", and added a partial unique index on (tenant + channel + group + user) (migration 0011, upgrading detaches duplicate conversations from the group, keeping history).
- WhatsApp messages are written to the DB before acknowledging (migration 0010): if the process crashed after acknowledgement, WhatsApp wouldn't resend and the message was lost. Now the event table doubles as an inbox, claimed with a conditional update before processing; the compensator (`python -m app.ops.channel_retry`, every minute) re-claims events not started or whose claimant vanished, up to 3 times, then replies with the fallback line.
- WhatsApp event de-duplication moved from process memory to the database (migration 0007): a WhatsApp-resent event landing on another worker, or after a restart, used to be answered again; now an "insert only if absent" check means even two arriving at once process only once.
- The permission-matrix test walks every endpoint: a new endpoint missing permissions fails CI. This caught and fixed two issues — customers could read the tenant risk limit, and a WhatsApp callback with no token configured accepted everything.
